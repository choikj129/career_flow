# 기능 워크플로우

요청: $ARGUMENTS

이 절차는 **메인 세션**이 진행한다. 서브에이전트는 다른 서브에이전트를 부를 수 없다. 그래서 단계 사이의 전달, 사용자 확인, 반복 횟수 관리는 메인 세션이 맡는다.

## 0. 준비

1. 작업 이름(kebab-case)을 정한다. 예: `tailored-resume`.
2. 작업 기록 `docs/work/<작업 이름>.md`를 만든다. 형식은 `docs/work/_template.md`를 따른다. 이 파일이 단계 사이의 전달 문서다. 모든 단계의 결과와 상태를 여기에 적는다.
3. 브랜치를 만든다: `feat/<작업 이름>`(`.claude/rules/git.md`).
4. 진행 상황은 작업 목록(`update_plan`)에 단계별로 보여 준다.

## 1. 설계: product-planner

- product-planner를 부른다. 넘길 것:
  - 요청
  - 작업 기록 경로
  - 관련 문서: 기획서, 단계 계획, `docs/decisions.md`
- planner가 하는 일:
  - 설계를 작업 기록의 "설계" 절에 쓴다.
  - 필요한 기획·화면·계획 문서를 고친다.
  - 정할 것 초안을 낸다.
- 결과 처리(보고서 끝 `상태`를 본다):
  - `설계 완료`: 2단계로 간다.
  - `결정 필요`: 5단계(결정 요청)를 먼저 한다.

## 2. 사용자 검토 (필수, 건너뛰지 않음)

- 사용자에게 설계 요약과 작업 기록 링크를 보여 주고 **검토를 요청한다**.
  - 요약에는 무엇을 만드는지, 바뀌는 문서, 정할 것을 담는다.
  - 질문은 하나만 한다. 버튼은 "승인" / "고칠 점 있음"이다.
- 사용자가 승인하기 전에는 developer를 부르지 않는다.
- 고칠 점이 있으면 그 내용을 planner에게 넘겨 1단계를 다시 한다.
- 승인을 받으면 작업 기록에 승인 날짜를 적는다. 사용자가 구현을 지시한 것으로 본다.

## 3. 개발: developer

- developer를 부른다. 넘길 것:
  - 작업 기록 경로
  - 승인된 설계
  - 브랜치 이름
  - 이전 회차의 리뷰 "고쳐야 할 목록"(있을 때)
- 결과 처리(`상태`를 본다):
  - `완료`: 4단계로 간다.
  - `결정 필요`: 5단계
  - `설계 필요`: 6단계
  - `실패`: 7단계
- 메인 세션은 보고만 믿지 않는다. `git log`와 `npm test`로 직접 확인한다.

## 4. 검증: code-reviewer

- code-reviewer를 부른다. 넘길 것:
  - 작업 기록 경로
  - 검토 범위(커밋 범위)
  - 설계
  - 이전 회차 목록
- 결과 처리(`상태`를 본다):
  - `통과`: 8단계(마무리)
  - `수정 필요`: 고쳐야 할 목록을 developer에게 넘겨 3단계를 다시 한다.
    - **다시 개발 요청은 최대 2회다.** 첫 검증 후 1회, 두 번째 검증 후 1회.
    - 세 번째 검증에서도 필수 항목이 남으면 더 반복하지 않고 7단계로 간다.
  - `결정 필요`: 5단계
  - `설계 필요`: 6단계
- 회차마다 작업 기록의 "검증 회차" 표에 회차, 결과, 남은 항목 수를 적는다.

## 5. 결정 요청 (어느 단계에서든)

필수·중요 결정이 나오면 `.claude/rules/ask-first.md`를 따른다.

1. 그 결정에 걸린 작업을 **멈춘다**. 결정과 상관없는 서브에이전트 작업은 계속해도 된다.
2. `docs/decisions.md`에 `D-번호`로 적는다. 배경, 선택지, 추천, 바뀌는 것을 쓴다.
3. 사용자에게 결정을 요청한다. 질문은 하나만 하고, 첫 버튼을 추천안으로 둔다.
4. 답을 받으면:
   - decisions.md의 "결정된 것"으로 옮긴다.
   - 작업 기록에 적는다.
   - **멈췄던 단계부터** 다시 진행한다. 설계에 영향이 있으면 6단계로 간다.

## 6. 설계로 되돌리기 (어느 단계에서든)

developer나 code-reviewer가 `설계 필요`를 내면:

1. 개발·검증을 **멈춘다**.
2. 설계가 필요한 이유와 근거를 작업 기록의 "재설계" 절에 적는다.
3. product-planner에게 그 부분의 설계를 맡긴다(1단계).
4. **2단계 사용자 검토를 다시 거친다.**
5. 승인되면 3단계부터 다시 한다. 재설계 뒤에는 검증 반복 횟수를 새로 센다.
6. 재설계는 한 작업에 최대 2회다. 3번째가 필요하면 7단계로 간다.

## 7. 해결하지 못함

반복 한도를 넘거나, 같은 실패가 되풀이되거나, 환경 문제로 진행할 수 없으면 멈춘다. 작업 기록의 "실패" 절과 사용자에게 다음을 **정확히** 적는다.

- **무엇이 실패했나**: 테스트 이름, 명령, 화면, 검토 항목
- **실제 출력**: 오류 메시지, 실패한 단언(그대로 붙인다)
- **원인**: 확인한 원인과 추정한 원인을 구분하고, 근거(`경로:줄`)를 단다.
- **시도한 것**: 회차별로 무엇을 바꿨고 결과가 어땠는지
- **남은 선택지**: 다음에 할 수 있는 것과 각각의 비용·위험

이 상태에서는 커밋만 하고 `main`에 병합하지 않는다. 브랜치는 남겨 둔다.

## 8. 마무리

검증 `통과`와 함께 다음이 모두 맞으면 `.claude/rules/git.md`대로 커밋하고 `main`에 병합한 뒤 브랜치를 지운다.

- `npm test`, `npm run test:e2e`(화면 변경 시), `npm run lint`, 타입 검사, 빌드가 모두 실패 0
- 열린 결정이 없음

그다음 할 일:

- 작업 기록의 상태를 "완료"로 바꾸고 결과를 요약한다.
- `CLAUDE.md`의 "현재 단계"가 바뀌었으면 고친다.
- 사용자에게 알린다. 만든 것, 검증 회차, 병합 커밋, 사용자가 직접 확인해야 할 것(수동 케이스)을 담는다.

## 서브에이전트에게 넘길 때 공통으로 넣을 것

- 작업 기록 경로. 결과도 그 파일에 쓰라고 한다(planner와 developer). reviewer는 보고서만 내고, 메인 세션이 작업 기록에 옮긴다.
- 브랜치 이름과 Git 규칙: 경로를 지정해서 커밋한다. `main` 병합과 push는 하지 않는다.
- 실제 `claude` 호출 허용 횟수(기본 0회). 실제 채용 사이트 접속 금지.
- 보고서 끝에 `상태` 블록을 쓰라는 요청(`.claude/rules/workflow.md`의 형식).
