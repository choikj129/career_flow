## 1. 설계 (product-planner)

### 검토할 것 (사용자용, 재설계 2 기준)

1. 정리하신 **프로필 방식** 그대로 갑니다: 기본 서류(백엔드·FDE) + 공고마다 부품 교체·순서 변경(D-26).
2. 가이드·작성 규칙·마스터스토리·기본 서류 md는 앱 "서류 키트" 화면에서 골라 올립니다. 고치면 다시 올립니다(D-27).
3. **프로필 추천은 공고 분석 때 AI가 합니다**(D-28). 프로필마다 추천도(%)와 근거 단어, 추가 조정 추천이 나옵니다. 분석 1회에 같이 하므로 호출은 늘지 않습니다.
4. 맞춤 이력서 탭에서 추천도 높은 순으로 보고 직접 고릅니다. 분석 탭에도 "추천 프로필 82%" 한 줄이 나옵니다.
5. 키트를 올리기 전에 분석한 공고는 추천이 없습니다. 그때는 공고 단어 수로 대신 보여 주고, [AI 추천 받기]를 누르면 공고를 다시 분석합니다(1~2분).
6. [맞춤본 만들기]는 AI 없이 즉시 조립합니다. [공고 용어 맞추기]와 다듬기만 AI를 쓰고, 마스터스토리에 없는 숫자·금지 표현·자기소개 변경은 앱이 찾아 줍니다.
7. 결과가 부족해 보이면 **이력서를 만드시는 작업 공간**에 요청할 수 있습니다. 앱이 요청문(공고, 고른 프로필과 추천도, 조립 요약, 걸린 검사)을 만들어 주면 [복사]해서 그 작업 공간에 붙여 넣습니다(**D-30**, 결정 필요).
8. 작업 공간에서 만든 이력서.md·경력기술서.md는 앱에 [결과 올리기]로 넣습니다. 같은 검사를 받고, 지원 기록과 통계에 "맞춤"으로 들어갑니다.
9. 앱이 그 작업 공간을 직접 실행하거나 그 폴더에 쓰지는 않습니다. 앱이 데이터 폴더 밖을 다루지 않는다는 원칙을 지키고, 사용량이 모르게 늘지 않게 하기 위해서입니다.
10. 요청을 권하는 때: 추천도 1등이 60% 미만, 용어 맞추기 뒤에도 "확인 필요"가 남음, 코드가 못 옮긴 추가 조정이 남음, AI가 "허용 범위로는 부족"이라고 표시함. 이때 화면 위에 권유 줄이 뜹니다. 버튼은 언제나 있습니다.
11. PDF는 쓰시는 PDF 스타일·파일명 규칙으로 만들고 앱에 저장하지 않습니다(D-25). 통계에는 맞춤/안 함 비교와 프로필별 통과율 표가 있습니다(D-24·D-29).
12. 개발·검증 중 실제 Claude 호출은 0회입니다. 병합 뒤 실제 키트를 올리고 공고 하나를 다시 분석해 보는 것이 실제 확인입니다.

### 재설계 1의 "검토할 것" (기록용)

1. 맞춤 이력서를 직접 정리하신 **프로필 방식** 그대로 앱에 옮깁니다: 기본 서류(백엔드·FDE) + 공고마다 부품 교체·순서 변경.
2. 가이드·작성 규칙·마스터스토리·기본 서류 md를 앱 "서류 키트" 화면에서 한 번에 골라 올립니다(D-27).
3. 공고 단어를 세어 추천하고 직접 확정합니다(재설계 2에서 AI 추천으로 바뀜, D-28 b).
4. 나머지(조립·용어 맞추기·검사·체크리스트·PDF·지원 기록·통계)는 재설계 2와 같습니다.

### 처음 설계의 "검토할 것" (D-23~D-25 결정 전, 기록용)

1. 공고 화면에 "맞춤 이력서" 탭이 생깁니다. 버튼 하나로 이 공고에 맞춘 사본을 만들고, 바뀐 곳·이유·사이트 이력서 고칠 곳·포트폴리오 순서를 보여 줍니다. 기본 이력서는 바뀌지 않습니다.
2. 없는 경력·수치·기술은 넣지 않습니다. AI가 회사명·기간·직무를 바꾸면 앱이 원래 값으로 되돌리고, 기본 이력서에 없는 숫자·기술은 노란 "확인 필요"로 보여 줍니다.
3. "이 문장 빼줘"처럼 적으면 새 버전(r2, r3…)이 생깁니다. 버전마다 PDF로 받을 수 있습니다.
4. 앱이 만드는 PDF는 단정한 기본 양식 하나입니다. 지금 직접 만들어 쓰시는 PDF와 모양이 다릅니다. 사이트 이력서로 지원할 때는 "수정 안내"의 문구를 [복사]해 붙여 넣으면 됩니다.
5. **D-23** 지금 [지원 완료]는 실제로 낸 PDF 파일을 남기지 않습니다. 이력서·경력기술서·포트폴리오 칸을 지원일 기준으로 자동으로 채우고, 맞춤본이 있으면 이력서 칸을 "맞춤 이력서 r번호"로 채우는 안을 추천합니다. 저장만 누르면 되는 것은 그대로입니다.
6. **D-24** 맞춤형 지원이 효과가 있는지 보려고, 통계에 "맞춤 이력서 / 맞춤 안 함" 서류 통과율 비교 칸을 더하는 안을 추천합니다. 맞춤본을 처음 낸 날부터의 지원만 비교합니다.
7. **D-25** 맞춤본 PDF는 파일로 따로 보관하지 않고, 필요할 때 같은 내용으로 다시 만드는 안을 추천합니다. 서류 파일 목록(이력서_날짜.pdf)과 섞이지 않습니다.
8. 서류 통과 결과는 지원 뒤 30일 가까이 걸려, 비교 숫자는 몇 주 뒤부터 의미가 생깁니다. 주 10~15곳이면 한 달쯤 지나야 "표본 적음" 표시가 사라집니다.
9. 개발·검증 중 실제 Claude 호출은 0회입니다. 병합 뒤 실제 공고 하나로 처음 만들어 볼 때(Opus 2회: 생성 1, 다듬기 1)가 실제 확인입니다.
10. 주 10~15곳을 맞춤으로 내면 분석과 합쳐 Claude 사용이 한 달 100회 안팎으로 늘 수 있습니다. 한도에 걸리면 다듬기를 줄이는 것이 먼저입니다.

### 목표와 범위

- 맞춤 이력서 생성·다듬기·리비전·변경 내역·확인 필요 경고·사이트 수정 안내·포트폴리오 활용·PDF(기획서 7.5, 11장). 기본 이력서 PDF와 버전 "직전 버전과 비교"(D-07에서 승인된 것).
- (D-23 a) [지원 완료]와 기록 수정 창이 실제로 낸 서류를 기록: 이력서(맞춤 리비전 / 이력서 파일 / 모름), 경력기술서·포트폴리오(파일 / 없음 / 모름). 기본값이 모두 채워져 저장만 누르면 된다.
- (D-24 a) 통계 "맞춤 이력서 효과" 칸과 서류 버전별(이력서) "맞춤 이력서" 묶음. 대시보드 이력서별 보기도 같은 묶음.
- 지어내기 금지는 그대로: 프롬프트 맨 위 규칙 + 사실 칸 되돌림(새로 더함) + 수치·기술·경력 검사(사이트 수정 안내 문구의 수치까지 넓힘).
- 계획: `docs/plans/phase-3-tailored-resume.md` Task 1~7. PM 위임 묶음 제안: A = Task 1·2, B = 3, C = 4·7, D = 5, E = 6.

### 만들지 않는 것

- 채용 사이트 이력서 자동 수정·자동 지원(비목표).
- 맞춤 PDF 파일 보관, 서류 파일 화면의 "맞춤 이력서" 묶음(D-25 a).
- PDF 템플릿 추가, 사용자 PDF 파일(이력서_날짜.pdf) 내용 읽기·수정.
- 맞춤 PDF에 경력기술서를 함께 냈는지 따로 기록(경력기술서 칸은 파일로 고른다).
- 지난 [지원 완료] 기록(기본 v번호)을 파일로 자동으로 바꾸는 일. 필요하면 수정 창에서 고친다.
- 주간 지원 목표(주 10~15곳) 추적 화면. 필요하면 따로 제안한다.

### 위험·빈틈

- 수치 검사 오탐·누락: 기준본에 있는 숫자를 다른 뜻으로 쓰면 못 잡는다(예: 다른 회사의 "3배"). 기술 이름은 부분 일치라 `Java`가 `JavaScript` 안에 있으면 못 잡는다. 경고는 보조 장치이고 사용자가 읽고 고치는 것이 전제다.
- 사실 옮기기: 프로젝트의 사실을 다른 회사 경력 성과로 옮기는 것은 코드로 못 잡는다. 프롬프트 규칙(그 회사에서 한 일만)으로만 막는다.
- 앱 PDF 양식이 사용자 PDF와 달라, 실제로는 맞춤본 PDF보다 "수정 안내"를 보고 직접 파일을 고칠 수 있다. 그 경우 이력서 칸을 무엇으로 고를지 헷갈릴 수 있다 → 화면 문서 3.7에 "PDF든 사이트 수정이든 맞춤 이력서 r번호를 고른다"로 적었다. 직접 고친 파일을 `이력서_날짜.pdf`로 넣고 그 파일을 고르면 맞춤으로 세지 않는다(한계).
- 비교의 한계: 맞춤 여부 말고도 회사·시기·사이트가 다르다. 칸 아래 문구로 알린다. 원인 분석까지는 하지 않는다.
- 사용 한도: 맞춤 1건 = 생성 1회 + 다듬기 n회(opus). 주 10~15건이면 한 달 수십~100회대.
- 3단계 전 [지원 완료] 기록(기본 v번호)은 그대로 남는다. 몇 건인지는 확인하지 않았다(개인 데이터라 `data/`를 읽지 않음). 통계에서 "기본 v1" 같은 묶음으로 보인다.
- 미리보기 iframe 응답은 사용자 내용이 담긴 HTML이다. 이스케이프 + CSP(스크립트 금지) + `sandbox`로 막는다.

### 재설계 1: 프로필 방식 (2026-11-20)

**확인한 것** (원본은 읽기만 함, 내용은 이 문서에 옮기지 않음)
- 사용자 가이드: 1장 직무별 기본 서류 표, 3장 부품 번호표·프로필 레시피 표·추가 조정 목록, 4장 자기소개 후보, 5장 허용 범위 표, 6장 체크리스트, 7장 지원 폴더·지원 현황 표. 모두 일정한 md 표·목록 모양이라 코드로 읽을 수 있다.
- 기본 서류 md: 제목 단계가 일정하다(자기소개, 핵심 역량 목록, 주요 성과 번호 목록과 들여쓴 하위 줄, 개인 프로젝트 3단계 제목, 기술 스택, 경력기술서 `## N.` 장과 `### N-k.`). 부품을 제목 글자로 찾을 수 있다.
- PDF 도구: md → HTML(제목·프로필 상자, 2단계 제목마다 섹션) → CSS → 브라우저 인쇄. 앱은 같은 구조를 TS로 옮기고 CSS만 키트에서 가져온다. md → HTML에 새 의존성 `marked`가 필요하다.
- 플랫폼 이력서는 기본 프로필 그대로 둔다는 것이 사용자 방식이다 → 사이트 수정 안내는 필요 없다.

**설계 판단과 이유**
1. 앱이 프로필 방식을 쓰는 순서: 추천(규칙) → 사용자 확정 → 조립(코드) → 공고 용어 맞추기(AI, 선택) → 자동 검사 + 체크리스트 → PDF/md. 기존 설계의 "AI 재작성 + 확인 필요 검사"는 2단계(AI)와 검사로만 남긴다. 조립을 코드가 하면 새 문장이 생길 틈이 없고 호출도 0이다.
2. 추천을 규칙으로 하는 이유: 가이드 2장 절차가 "공고 단어를 세어 프로필 고르기"이고, 단어 목록이 가이드 표에 있다. 결정적이고 테스트할 수 있으며 호출이 0이다. AI 의견은 용어 맞추기 결과 메모에 한 줄로만 받는다.
3. 키트를 구조로 읽는(파싱) 이유: 추천·조립·검사·통계 이름 모두 구조가 필요하다. md를 통째로 프롬프트에 넣는 방식은 추천·순서 검증이 안 된다. 대신 형식 규칙을 계획에 적고, 읽기 실패는 키트 화면에 구획·줄로 보인다.
4. 키트를 올리는 방식(D-27 a): 사용자가 원본을 자주 고친다. 메인 세션 복사를 거치지 않고 사용자가 바로 갱신할 수 있다. 앱이 `D:\`를 읽지 않는다는 결정은 그대로다(브라우저 파일 선택은 사용자 행동). 키트는 버전마다 보관해 옛 맞춤본의 [보기]·다시 조립·다듬기 기준이 된다. 리비전은 md 원문을 가지므로 PDF 재생성에는 키트가 없어도 된다(스타일만 그 키트의 것을 쓴다).
5. 앱 기본 이력서(JSON)와 기본 서류의 관계: JSON은 공고 분석 입력으로만 남긴다. 분석까지 키트 md로 바꾸는 것은 이번 범위를 넘으니 다음 작업 후보로 둔다. 예전 결정 "직무별 변형 무시, `이력서_YYYYMMDD.pdf`만"은 지난 서류 파일(7.9)에만 해당하도록 기획서 7.11에 정리했다(충돌 해소, 결정 변경 아님).
6. 맞춤본 위치: D-25 a대로 앱은 저장하지 않는다. 사용자 지원 폴더 양식(공고 요약·이력서·경력기술서·PDF)과 같은 이름으로 내려받기를 준다(`공고.md` 포함). 앱이 데이터 폴더 밖에 쓰지 않으므로 옮기는 것은 사용자가 한다.
7. 지원 현황 표: 앱 지원 기록(제출 서류 = 프로필·추가 조정·맞춤 여부) + 통계(프로필별)로 대신한다. 내보내기는 만들지 않는다(필요하면 나중에).
8. 지원 기록에 남는 것: `tailored`(리비전 → 직무·프로필·추가 조정·키트) 또는 `kit`(기본 서류 그대로: 직무·기본 프로필·키트). 칸 추가 없이 JSON 종류만 넓힌다.

**메인 세션이 처음 키트를 넣을 때 (D-27 b일 때만 필요)**: 복사할 파일 목록은 보고서에만 적었다(공개 저장소라 이 문서에는 개인 폴더·파일 이름을 적지 않는다). 역할: 가이드, 작성 규칙, 마스터스토리, 직무별 이력서·경력기술서 md 4개, PDF 스타일(PDF 도구 스크립트의 CSS). 복사하지 않는 것: 지원 전략 메모, 지원 현황 표, 이미 만든 PDF·HTML, 질문 메모, 백업.

**1. 프로필 추천을 공고 분석에 넣기 (D-28 b, 계획 Task 3b)**
- 어디서: 기존 `analyze_posting` 작업의 프롬프트와 출력 스키마에 "프로필 추천" 칸을 더한다. 공고 등록 때 이미 1회 실행되므로 **호출이 늘지 않는다**.
- 입력: 키트에서 만든 프로필 표(직무, 프로필 id·이름·기본 여부·공고 단어, 추가 조정 id·트리거 단어). 자기소개·서류 내용은 넣지 않는다(분석에는 필요 없고, 프롬프트가 짧아진다).
- 출력: 직무와 이유, 그 직무의 프로필마다 추천도 0~100(프로필마다 따로, 합이 100 아님)·근거 키워드(공고 본문에 있는 단어만)·한 줄 이유, 추가 조정마다 추천 여부·키워드. 코드가 정리한다: 모르는 id 버림, 빠진 프로필 0%, 정렬, 공고에 없는 키워드 제거, 키트 id 붙이기.
- 추천도를 독립 점수로 한 이유: "합 100%"는 프로필이 서로 겹치는 경우(범용과 특화) 숫자가 어색하고, 사용자가 원한 "프로필별 추천도"를 각각 읽기 쉽다.
- 키트 버전 기록: 결과에 `kitId`. 맞춤 탭은 지금 키트와 같으면 그대로, 다르면 지금 키트에 있는 프로필만 보이고 "이전 키트 기준 추천" 표시.
- 분석이 키트보다 먼저인 경우(키트 없이 분석, 키트를 나중에 올림, 옛 분석): 추천 칸이 없다. 맞춤 탭은 규칙 단어 세기로 대신 보이고 `[AI 추천 받기 (다시 분석)]`.
- 다시 추천하는 방법: **기존 [다시 분석]을 쓴다.** 추천만 하는 작업을 따로 만들지 않는다. 이유: 추천도 공고 전체를 읽어야 해서 입력이 분석과 거의 같고(아끼는 양이 작음), 작업 종류·설정·테스트가 늘며, 다시 분석은 이미 있는 기능이다. 부작용: 적합도도 새로 매겨진다(이전 결과는 분석 기록에 남는다).
- 규칙 기반 단어 세기는 **대체로만 남긴다.** AI 추천이 없을 때 즉시(호출 0) 고를 수 있게 하기 위해서다. AI 추천이 있으면 보이지 않는다(두 숫자를 나란히 두면 헷갈림).
- 분석 프롬프트 변경은 분석 결과 모양을 바꾼다. 옛 결과는 칸이 없어도 읽히도록 저장용 스키마에서 선택 칸으로 둔다(TC-KIT-33).

**2. 이력서 작업 공간에 공고 특화 이력서 요청 (D-26 추가, 계획 Task 9, D-30 초안)**
- 사용자는 이력서를 앱 밖의 자기 Claude Code 작업 공간(원본 폴더, 자체 규칙·PDF 도구)에서 만든다. 앱 조립·용어 맞추기는 허용 범위가 좁아(순서·부품·용어만) 문장을 새로 짜야 하는 공고에는 부족할 수 있다. 그때 그 작업 공간에 맡기는 길을 둔다.
- 검토한 방법
  - (가) **앱이 요청문을 만들고 사용자가 복사해 붙여 넣기 + 결과 md를 앱에 올리기** — 앱 권한·비용 변화 없음. 작업 공간의 규칙·도구를 그대로 쓴다. 사용자 손이 두 번(붙여 넣기, 올리기) 든다.
  - (나) 앱이 작업 공간 폴더를 작업 폴더로 `claude -p` 실행, 결과를 그 폴더에 씀 — 앱이 데이터 폴더 밖을 읽고 쓴다(기존 결정과 충돌), 파일 쓰기 도구를 허용해야 하고(현재 규칙: 모든 작업에서 금지), 작업 공간 규칙·하위 에이전트까지 실행되어 비용이 크고 예측이 어렵다. 앱 작업 큐가 그동안 막힌다.
  - (다) 앱이 요청 파일만 데이터 폴더에 두고 작업 공간이 그 파일을 읽기 — 작업 공간이 앱 데이터 폴더 경로를 알아야 하고, (가)의 [요청문 받기]와 다를 것이 없다.
- 추천: **(가)**. 결과 올리기까지 넣는 이유: 작업 공간에서 만든 맞춤본도 같은 검사, 지원 완료 기본값, "맞춤"·프로필 통계에 들어가야 효과를 잴 수 있다(사용자 목적).
- 요청을 권하는 기준(코드, 상수로 조정 가능): ① 추천도 1등 < 60% ② 용어 맞추기·다듬기 뒤에도 "확인 필요" 경고가 남음 ③ 코드가 못 옮긴 추가 조정이 남음 ④ 용어 맞추기 AI가 `needsWorkspace: true`(허용 범위로는 공고에 잘 못 맞춤). 하나라도 맞으면 권유 줄, 아니어도 버튼은 늘 있다(사용자 판단이 최종).
- 요청문에는 공고 본문 전문과 앱이 고른 프로필·조립 요약을 넣고, 조립 md 전문은 넣지 않는다(작업 공간에 기본 서류가 있다). 틀 문장만 코드에 두고 개인 내용은 실행 때 채운다.
- 작업 공간 결과 리비전은 자기소개를 되돌리지 않는다(작업 공간이 새로 쓸 수 있음). 바뀌면 경고로만 보인다. 수치 검사는 같다.

**위험·빈틈**
- AI 추천도는 매번 조금씩 다를 수 있다(같은 공고를 다시 분석하면 숫자가 바뀜). 화면에 "AI 추천"이라고 밝히고, 최종 선택은 사용자다.
- 분석 프롬프트가 길어지고 출력 칸이 늘어 분석 형식 오류가 조금 늘 수 있다(같은 세션 재요청 1회는 그대로).
- 키트를 바꾼 뒤 이미 분석한 공고들의 추천을 한꺼번에 다시 받는 기능은 없다(공고마다 [다시 분석]). 필요하면 나중에.
- 작업 공간 요청은 사용자 손을 거친다. 결과를 올리지 않고 지원하면 그 지원은 맞춤 통계에 "맞춤"이 아니라 그때 고른 값(기본 서류·파일)으로 들어간다. 지원 완료 창 안내로 줄인다.
- 작업 공간 결과 md의 구조가 기본 서류와 많이 다르면 구조 경고가 많이 뜰 수 있다(경고일 뿐 저장은 됨).
