# Career Flow — 개인 취업 활동 관리·분석 도구 설계

- 작성일: 2026-11-16
- 상태: 승인됨 (2026-11-16). 이후 결정은 `docs/decisions.md`에 기록하고 이 문서에 반영한다.
- 표기: **[사용자 결정]** 은 대화에서 사용자가 정한 것, **[제안]** 은 설계자가 채운 판단(사용자 확인 대상), 표시 없는 것은 요구사항 그대로.

---

## 1. 왜 만드는가

여러 채용 사이트(리멤버·원티드·그룹바이·잡코리아 등)에 이력서를 따로 등록해 쓰면, 한 곳을 고칠 때마다 나머지를 손으로 맞춰야 하고 모든 회사에 같은 이력서·경력기술서·포트폴리오를 내기 쉽다. 지원도 사이트마다 따로 하게 되어 **어느 사이트에서 어느 회사에 언제 지원했는지 한눈에 보기 어렵고, 같은 회사에 중복 지원할 위험이 있다.**

이 도구는 다음을 해결한다.

1. 지원 기록을 한곳에 모아 **회사 이름으로 검색하면 언제·어디서·어떤 포지션에 지원했는지 바로** 보이게 한다.
2. 공고 링크를 넣으면 **바로 분석**해 적합도, 잘 맞는 점, 부족한 점을 알려준다.
3. 공고·회사에 맞춘 **맞춤 이력서**를 만들어 준다(PDF + 사이트 이력서 수정 안내).
4. 지원한 공고에 대해 **면접 준비 자료**(회사 조사, 예상 질문, 준비할 것)를 만들어 준다.

## 2. 누가, 어디서 쓰는가

- **사용자 1명이 쓴다.** [사용자 결정] 회원가입·로그인·다중 사용자 없음.
- 사용자 PC(Windows 11)에서 실행하고, 브라우저로 `localhost`에 접속해 쓴다.
- 모든 데이터는 PC 안에 저장된다. 외부로 나가는 것은 Claude Code가 처리하는 내용뿐이다.

## 3. 목표 · 비목표 · 반목표

**목표**
- 회사 검색 한 번으로 과거 지원 여부를 확인한다 → 중복 지원 0건.
- 공고 링크 등록 → 2분 안팎으로 분석 결과를 화면에서 본다.
- 맞춤 이력서 PDF를 받아 그대로 첨부해 제출할 수 있다.
- 지원 이후 면접까지 필요한 자료가 그 공고 화면 하나에 모인다.
- 추가 입력 없이 지원 기록만으로 서류 통과율을 기간·사이트·서류 버전별로 본다(7.10).

**비목표 (만들지 않음)**
- 채용 사이트에 자동 지원, 사이트 이력서 자동 수정, 사이트 자동 로그인·크롤링 봇. (약관·계정 차단 위험)
- 지원 완료 알림(메일·메신저) 자동 수집. [사용자 결정: 알림 경로가 여러 가지라 공고 링크를 직접 등록하는 방식으로] 앱은 메일함·메신저에 접속하지 않는다.
  - 예외(2026-11-19 사용자 결정): 앱을 쓰기 전의 지난 기록은 **한 번만** 옮긴다. 원티드·잡코리아·리멤버의 "지원 완료" 메일은 메인 세션(Claude 데스크톱의 메일 연결)이 읽어 DB에 직접 넣고, 그룹바이 등 나머지는 앱의 직접 입력(7.7)으로 넣는다. 계속되는 수집 기능은 만들지 않는다.
- 다른 사람과 공유, 모바일 앱, 클라우드 배포.
- 포트폴리오 파일(디자인/PDF) 자체를 편집하는 기능.

**반목표 (이렇게 되면 기능이 돌아가도 실패)**
- 맞춤 이력서가 **없는 경력·성과·기술을 지어내는 것.** 표현 조정·순서 변경·강조만 허용한다.
- 기록 남기는 일이 지금보다 귀찮아져서 결국 안 쓰게 되는 것. 지원 기록은 "링크 붙여넣기 + 지원 완료 클릭" 이상의 입력을 요구하지 않는다.
- 공고가 마감·삭제된 뒤 분석·면접 준비 근거가 사라지는 것. 공고 본문은 등록 시점에 반드시 저장한다.

## 4. 제약

- **AI 처리는 전부 사용자 PC의 Claude Code CLI를 호출해 구독 사용량으로 처리한다. Anthropic API 키·API 과금은 쓰지 않는다.** [사용자 결정]
  - 이용 조건: Claude Code 공식 문서(Legal and compliance)상, 본인이 **수정하지 않은 Claude Code 바이너리에 본인 구독으로 로그인**해 쓰는 것은 허용되며 구독 한도는 "개인의 일반적 사용"을 전제로 한다. 금지되는 것은 제3자에게 Claude 로그인을 제공하거나 구독 자격 증명을 대신 다루는 것이다. 따라서 이 앱은 다음을 지킨다.
    - Claude Code 로그인 정보(토큰·세션)를 읽거나 저장하거나 다루지 않는다. 앱은 `claude` 명령을 실행하기만 한다.
    - 다른 사람에게 배포·제공하지 않는다.
    - 사용량은 개인 사용 수준(월 수십 건)을 유지한다.
- 4개 채용 사이트 모두 지원 내역을 가져올 공개 API가 없다. 지원 기록은 사용자가 직접 등록한다(지난 기록의 한 번 이관은 3장 예외).
- 원티드·리멤버 등은 공고 본문이 자바스크립트로 그려지고, 일부는 로그인해야 보인다. 단순 HTTP 요청으로는 본문을 못 읽을 수 있다.
- Windows 명령줄 길이 제한(약 32K자)이 있으므로 Claude Code에 큰 입력(이력서·공고 본문)을 **명령줄 인자로 넘기지 않는다** (표준입력 또는 파일로 전달).
- Claude Code 실행 1회당 시작 비용이 있어 응답이 API보다 느리다(작업당 30초~수 분).
- Claude Code 사용 한도는 사용자의 평소 Claude Code 사용과 공유된다.

## 5. 검토한 접근 방식

| 방식 | 내용 | 장점 | 단점 | 결과 |
|---|---|---|---|---|
| A. 로컬 웹앱 + Claude API | 앱이 Anthropic API로 모든 AI 작업 | 한 화면, 빠름 | API 별도 과금(전부 Opus 기준 월 약 $17 추정) | 출발점이었으나 아래로 대체 |
| A′. 로컬 웹앱, 분석만 API + 나머지는 Claude Code에서 명령 실행 | 앱이 Claude Code에 붙여넣을 명령을 복사해 줌 | API 비용 절감(월 약 $8), 대화로 다듬기 쉬움 | 창 전환 필요, API 키는 여전히 필요 | 검토 후 제외 |
| **A″. 로컬 웹앱 + 앱이 Claude Code CLI를 직접 호출** | 앱 서버가 `claude -p`를 실행하고 결과(JSON)를 DB에 저장·표시 | 추가 비용 0, 한 화면, 대화로 다듬기 가능, Claude Code의 웹 검색 활용 | 느림, 사용 한도 공유, CLI 옵션 변경에 영향받음 | **채택** [사용자 결정] |
| B. Claude Code 중심 + 가벼운 대시보드 | 분석은 사용자가 Claude Code에서 명령 실행 | 만들 것 적음 | "링크 넣으면 바로 분석" 흐름이 안 됨 | 제외 |
| C. 노션 등 기존 도구 + Claude 연동 | DB·화면을 노션으로 | 만들 것 거의 없음 | PDF 출력·중복 경고 등 원하는 대로 안 됨 | 제외 |

**[제안]** AI 호출부는 하나의 인터페이스(`AiRunner`)로 감싸서, 나중에 설정만으로 API 방식(A)으로 바꿀 수 있게 한다. 이번 범위에서는 Claude Code CLI 구현만 만든다.

## 6. 핵심 사용 흐름

### 6.1 평소 지원 흐름 [사용자 결정]

```
① 대시보드에서 회사 검색 → 과거 지원 이력 확인
② 공고 링크 등록 → 등록과 동시에 자동 분석 시작
③ 분석 결과 확인 (적합도 / 잘 맞는 점 / 부족한 점)
④ (선택) 맞춤 이력서 생성 → 필요하면 대화로 수정 → PDF 받기 / 사이트 수정 안내 보기
⑤ 실제 사이트에서 지원 → 앱에서 [지원 완료] 클릭 → 관리 목록에 추가
⑥ 서류 결과에 따라 상태 변경 → 면접 잡히면 [면접 준비 생성]
```

- 분석만 하고 지원하지 않은 공고는 관리 목록과 섞이지 않게 **"분석한 공고"** 목록에 남는다. [제안]
- ②에서 이미 지원한 적 있는 회사면 **경고 배너**를 띄운다(사용자가 먼저 검색하더라도 깜빡했을 때를 대비한 안전장치). [제안]

### 6.2 처음 설정 흐름 [제안]

```
① 기본 이력서 등록: 기존 이력서·경력기술서·포트폴리오 PDF 업로드(또는 텍스트 붙여넣기)
   → Claude가 항목별 구조로 정리 → 사용자가 검토·수정 후 저장
② 희망 조건 입력 (연봉, 지역, 회사 규모, 원격 여부 등 — 모두 선택 입력)
③ 기존 지원 내역 가져오기: 각 사이트 "지원 현황" 화면을 복사해 붙여넣기 또는 캡처 업로드
   → Claude가 표로 추출 → 사용자가 검토·수정 후 일괄 등록
```

③이 없으면 처음엔 중복 검사가 소용없으므로 1차 범위에 포함한다.

## 7. 기능 상세

### 7.1 기본 이력서 (마스터)

- 앱 안에 **기준본 하나**를 둔다. 구성:
  - 기본 정보(이름·연락처·링크) — PDF 출력용
  - 한 줄 소개/요약
  - 경력: 회사, 기간, 직무/직급, 담당 업무, 성과(항목별 문장)
  - 프로젝트: 이름, 기간, 소속, 역할, 사용 기술, 성과, 링크
  - 기술 스택(분류별), 학력, 자격증·수상·교육
  - 경력기술서 본문(경력별 상세 서술)
  - 포트폴리오: 파일/링크와, Claude가 정리한 요약(프로젝트별)
- 기준본을 저장할 때마다 **버전**을 남긴다(이전 버전 보기·비교 가능).
- 등록 방식: PDF/DOCX 업로드 또는 텍스트 붙여넣기 → Claude가 위 구조로 추출 → 사용자 편집 화면에서 수정 후 저장. 이후 수정은 앱의 편집 화면에서 직접.
- **희망 조건**(선택): 희망 연봉 범위, 근무 지역, 원격/하이브리드, 회사 규모, 선호/기피 산업. 분석 시 조건 적합 여부 표시에 쓴다.

### 7.2 대시보드 · 회사 검색

```
[검색: 토스                ]  [상태 ▾] [사이트 ▾] [기간 ▾]
회사      포지션        사이트   지원일      상태     적합도
토스      Server Dev   원티드   2025-10-03  서류합격  82
토스뱅크  백엔드        리멤버   2025-09-12  불합격    71
────────────────────────────────────────────────
이번 달 지원 12 · 서류합격 3 · 면접 대기 2
[분석한 공고 5건 보기]
```

- 검색 대상: 회사 표시명, 법인명, 사용자가 등록한 별칭. 대소문자·공백·`(주)`·`주식회사` 차이는 무시한다. [제안]
  - 예: "토스"로 검색하면 "토스", "토스뱅크", 법인명 "비바리퍼블리카"로 저장된 건까지 보인다(별칭/부분일치).
- 검색 결과 행을 누르면 그 공고 상세(분석·제출한 이력서·면접 준비)로 이동.
- 요약 지표: 이번 달 지원 수, 상태별 개수, 사이트별 개수. [제안]
- 상태 필터의 서류합격, 과제·코딩테스트, 면접, 최종합격은 **그 단계를 거친 기록**을 모두 보여 준다(예: 서류합격 뒤 불합격도 "서류합격"에 나옴). 과제·코딩테스트를 거친 기록은 서류합격도 거친 것으로 본다. 지원·불합격·지원취소는 지금 상태 기준. 상태별 보드의 칸은 지금 상태 기준이다. (2026-11-19 사용자 요청, 화면 문서 1장)
- 사이트별·이력서별 묶음 머리의 서류 통과율은 통계(7.10)와 같은 정의를 쓴다(D-18).
- 요약 줄에 "통계 보기 →"를 둔다. 누르면 통계 화면(7.10)으로 간다(D-19).

### 7.3 공고 등록과 분석

**등록**
- 입력: 공고 URL. 실패 시를 대비해 **공고 본문 직접 붙여넣기** 입력도 둔다.
- 사이트는 URL 도메인으로 자동 판별(리멤버/원티드/그룹바이/잡코리아/홈페이지 지원/기타). 홈페이지 지원은 회사 홈페이지에서 직접 지원한 경우로 주소로는 판별하지 않고 직접 고른다. 기타면 사용자가 사이트 이름을 고를 수 있다(회사 채용 페이지, 지인 추천 등). [제안]
- 같은 URL을 다시 등록하면 새로 만들지 않고 기존 공고로 이동한다. [제안]
- 잘못 등록한 공고는 삭제할 수 있다. 단, 지원 기록이 없는 공고만이며 분석·맞춤 이력서·면접 준비도 함께 지운다. [결정 D-02]
- 본문 추출은 앱이 Playwright로 페이지를 열어 수행한다(8장). 추출된 본문 텍스트와 원본 URL·추출 시각을 **반드시 저장**한다.

**분석 (등록 즉시 자동 실행)** [사용자 결정]
- 입력: 공고 본문 + 기본 이력서(최신 버전) + 희망 조건.
- 출력(정해진 JSON 형식):
  - 공고 정보 추출: 회사명(표시명/법인명), 포지션, 경력 요건, 고용 형태, 근무지, 마감일, 연봉 정보(있으면), 주요 업무, 필수 요건, 우대 사항, 기술 스택
  - **적합도 점수 0–100** 과 항목별 근거: 필수 요건 / 우대 사항 / 경력 연차 / 기술 스택 / 도메인 / 희망 조건 [제안: 항목 구성]
  - **잘 맞는 점**: 공고 요건 ↔ 내 경력 근거 연결
  - **부족한 점** — 두 종류로 구분 [제안]
    - "있는데 이력서에 안 드러난 것" → 맞춤 이력서에서 보완
    - "실제로 없는 것" → 면접에서 어떻게 답할지 준비할 것
  - 희망 조건과 맞지 않는 점(있으면)
  - 맞춤 이력서가 필요한지에 대한 한 줄 판단
- 분석 결과는 공고에 붙여 저장하고, 기본 이력서 몇 번째 버전 기준인지 함께 남긴다.
- 사용자가 [다시 분석]으로 재실행할 수 있다(이전 결과는 덮어쓰지 않고 이력으로 남김). [제안]

### 7.4 지원 완료와 상태 관리

- 공고 화면의 **[지원 완료]** → 지원일(기본 오늘), 지원 사이트(기본 공고의 사이트), 제출 서류를 확인 후 저장 → 관리 목록에 추가. [사용자 결정 + 기본값은 제안]
  - 제출 서류(3단계, D-23 결정): 실제로 낸 것을 적는다. 이력서 = 이 공고의 맞춤 리비전(프로필 포함) / 기본 서류 {직무}(키트 기본 서류 그대로, 기본 프로필) / 이력서 파일(7.9) / 모름. 경력기술서·포트폴리오 = 파일 / 없음 / 모름. 기본값: 이력서는 맞춤본이 있으면 최신 맞춤 리비전, 없고 키트가 있으면 추천 직무의 기본 서류, 그것도 없으면 지원일 기준 이력서 파일. 경력기술서·포트폴리오는 7.9 규칙. 기본값 그대로 저장만 눌러도 된다.
  - 3단계 전 [지원 완료] 기록은 "기본 이력서 v번호"로 남아 있다. 그대로 두고, 필요하면 수정 창에서 파일로 고친다.
- 상태: `분석함 → 지원 → 서류합격 → 과제·코딩테스트 → 면접(1차/2차/…) → 최종합격 | 불합격 | 지원취소` [제안]
  - 과제·코딩테스트(2026-11-20 추가): 과제, 코딩테스트, 사전 테스트를 하나로 기록한다. 차수는 없고 날짜·메모만 적는다. 두 번 있으면 한 번 더 저장한다. 거치지 않는 회사가 많으므로 면접·최종합격은 이 단계를 거친 것으로 보지 않는다. 상태는 텍스트 칸이라 DB 스키마 변경은 없다.
- 상태 변경 시 날짜를 기록해 타임라인으로 보여준다. 메모 입력 칸을 둔다. [제안]
- 한 회사에 여러 포지션 지원 가능(회사 1 : 공고 N).
- 지원 기록은 수정(회사, 포지션, 사이트, 출처, 지원일, 제출 서류)과 삭제(확인 후, 상태 이력 포함)를 할 수 있다. 삭제해도 공고는 남아 "분석한 공고"로 돌아간다. [결정 D-01]
- 사이트가 "기타"이면 출처 이름(예: 회사 채용 페이지, 지인 추천)을 적을 수 있다. 전에 쓴 이름을 다시 고를 수 있다. [결정 D-03]
- 같은 회사가 둘로 잡히면 공고 화면의 회사 연결 변경 창에서 합친다(공고·지원 기록·별칭이 한 회사로 모임). [결정 D-04]

### 7.5 맞춤 이력서

재설계 1 (2026-11-20): **프로필 방식** (D-26 추천안·결정 대기). 사용자가 정리한 공고 맞춤 방식을 앱으로 옮긴다: 범용 기본 서류 한 벌(직무별 이력서·경력기술서) + 공고마다 바꿔 끼우는 부품. 재료는 서류 키트(7.11)다.

- 흐름
  1. **프로필 추천** (D-28 추천안): 공고(분석 결과의 업무·요건·우대·기술 스택, 없으면 본문)에서 각 프로필의 공고 단어 수를 센다. 직무(예 백엔드/FDE)와 프로필, 추가 조정을 추천하고 많이 나온 단어 3개를 보인다. AI를 쓰지 않는다. 사용자가 확정한다.
  2. **조립** (앱 코드, 즉시): 기본 서류를 복사해 레시피대로 자기소개를 후보로 바꾸고, 핵심 역량·주요 성과·경력기술서 장 순서를 바꾸고(번호 다시 매김), 개인 프로젝트를 고른다. 구조로 옮길 수 있는 추가 조정도 적용한다. 새 문장이 생기지 않는다.
  3. **공고 용어 맞추기** (AI, 선택): 가이드의 허용 범위 표 안에서 같은 사실을 공고 단어로 바꾸고, 남은 추가 조정을 반영한다.
  4. **점검**: 앱의 자동 검사 + 가이드 체크리스트(직접 확인).
  5. **받기**: 이력서·경력기술서 PDF(키트 스타일)와 md, 공고 요약 md.
- 규칙
  - **마스터스토리에 없는 사실·숫자를 만들지 않는다.** 바뀌는 것은 부품·순서(코드)와 허용 범위 안의 용어(AI)뿐이다.
  - 앱이 코드로 확인한다: 조립본에 없던 수치(마스터스토리에 있으면 "새로 넣은 사실", 없으면 "확인 필요"), 쓰면 안 되는 표현, 자기소개 변경(조립본 값으로 되돌림), 제목·항목 수·장 순서 변경, 기술 스택 줄 변경, 다른 회사 이름.
- **대화로 다듬기**: 최신 리비전·요청·키트(작성 규칙·허용 범위·마스터스토리)를 새 실행에 넣는다(D-11). 같은 검사를 한다. 수정할 때마다 새 리비전.
- 사용자의 기본 서류와 앱 안 기본 이력서(7.1)는 절대 수정하지 않는다.
- 사이트에 등록한 이력서는 기본 프로필 그대로 둔다(사용자 방식). 그래서 처음 설계의 "사이트 이력서 수정 안내"와 "포트폴리오 활용 제안"은 만들지 않는다. 맞춤본은 첨부 PDF와 홈페이지 지원에 쓴다.
- 맞춤본과 파일의 관계 (D-25 결정)
  - 맞춤본 PDF·md는 앱에 파일로 보관하지 않는다. 리비전에 md 원문이 있어 언제든 같은 내용으로 다시 만든다. 서류 파일 목록(7.9)과 섞이지 않는다.
  - 사용자가 자기 지원 폴더(공고별 폴더)에 남기고 싶으면 [md 받기]·[PDF 받기]로 내려받아 옮긴다. 앱은 데이터 폴더 밖에 쓰지 않는다.
  - PDF는 키트의 스타일(사용자 PDF 도구와 같은 CSS)로 만들고, 파일명도 가이드 규칙(이름_서류_직무)을 따른다.
- 지원 완료 때 "맞춤 이력서 r번호"(프로필·추가 조정 포함) 또는 "기본 서류 {직무}"(기본 프로필)를 고른다(7.4). 통계가 맞춤 효과와 프로필별 서류 통과율을 센다(7.10). 사용자가 따로 쓰던 지원 현황 표는 앱의 지원 기록과 통계가 대신한다(내보내기는 만들지 않음).

### 7.6 면접 준비

- 공고 화면의 **[면접 준비 만들기]** (상태와 무관하게 실행 가능, 보통 서류합격 후).
- 입력: 공고 본문, 분석 결과, **실제 제출한 이력서 버전**(면접 질문은 제출한 이력서에서 나오므로) [제안]
- Claude Code가 웹 검색으로 회사를 조사한다.
- 출력:
  - 회사 개요: 사업·주요 제품, 규모, 최근 뉴스·투자, 기술 블로그·기술 스택 (출처 링크 포함)
  - 공고에서 읽히는 팀의 과제와, 내가 기여할 수 있는 점
  - 예상 질문: 기술 / 경력·프로젝트 꼬리 질문 / 인성·협업 / 회사·지원동기 — 각 질문마다 내 경력에서 꺼낼 답변 소재
  - 부족한 점 대응 전략(7.3의 "실제로 없는 것"에 대해)
  - 내가 면접관에게 물어볼 질문
  - 면접 전 체크리스트(알고 갈 것)
- 이것도 대화로 추가 요청 가능(예: "2차 임원면접용으로 다시"). 면접 차수별로 여러 개 만들 수 있다. [제안]

### 7.7 기존 지원 내역 가져오기 [제안]

- 사이트별 "지원 현황" 화면 텍스트 붙여넣기 또는 캡처 이미지 업로드.
- Claude Code가 회사·포지션·지원일·상태를 표로 추출 → 검토 표에서 수정·삭제 → 일괄 등록.
- 이렇게 들어온 건은 공고 본문 없이 "지원 기록만" 있는 상태로 저장된다(분석 없음).
- **직접 입력** (2026-11-19 사용자 결정): AI 없이 검토 표를 빈 행으로 열어 지난 기록을 적는다(예: 그룹바이처럼 메일이 없는 사이트).
  - 필수: 지원 사이트, 회사, 포지션, 지원일 [결정 D-16]. 기존 가져오기의 필수 칸과 같다.
  - 선택: 메모, 이력서·경력기술서·포트폴리오 파일(7.9). 지원일을 넣으면 파일이 자동으로 골라지고, 바꿀 수 있다.
  - 같은 회사·같은 지원일·같은 포지션 기록이 이미 있으면 "이미 있음"으로 체크를 끈다. 포지션만 다르면 "같은 날 기록 있음"만 보인다.
- 메일(원티드·잡코리아·리멤버)의 지난 기록은 앱 기능이 아니다. 메인 세션이 한 번 DB에 넣었고, 메모를 두 줄로 남겼다: 첫 줄 `메일 가져오기(사이트)` 또는 `수기 입력(그룹바이)`, 둘째 줄 `제출 서류: 이력서 YYYY-MM-DD|모름 / 경력기술서 … / 포트폴리오 …`. 둘째 줄은 7.9의 이관으로 제출 서류 칸에 옮긴다.

### 7.8 기본 이력서 변경 → 사이트 반영 체크리스트 [제안]

- 기본 이력서를 새 버전으로 저장하면, 이전 버전과의 차이를 바탕으로 **사이트별 반영할 내용**을 만든다(리멤버/원티드/그룹바이/잡코리아 각각 체크박스).
- 모든 사이트에 반영 체크하면 완료 처리. 사이트에 직접 접속해 고치는 것은 사용자가 한다.
- 지금 "한 곳 고치면 4곳 손으로 맞추기"를 체크리스트로 바꾸는 기능.

### 7.9 제출 서류 파일 (이력서·경력기술서·포트폴리오) [결정 D-15]

- 지난 지원에 **어떤 서류 파일을 냈는지** 남기고 다시 열어 보기 위한 기능이다. 앱 안의 기본 이력서(7.1, 내용 구조와 버전)와는 별개다.
- 서류 종류는 이력서 / 경력기술서 / 포트폴리오 세 가지다(자기소개서 없음). 직무별 변형본은 쓰지 않는다.
- 쓰는 파일은 `(이력서|경력기술서|포트폴리오)_YYYYMMDD.pdf` 형식만이다. **버전 날짜 = 파일 이름의 날짜.**
- 보관: 파일은 앱 데이터 폴더 `data/documents/<resume|career|portfolio>/`에 원래 이름(`이력서_YYYYMMDD.pdf` 등)으로 복사해 둔다(2026-11-19 복사 완료). 앱은 데이터 폴더 밖(예: 사용자의 서류 폴더)을 읽지 않는다.
- **등록 절차는 없다.** 앱은 이 폴더를 읽어 이름 규칙에 맞는 파일을 그대로 목록으로 쓴다. 새 파일은 폴더에 넣기만 하면 된다. 내용은 읽지 않는다(`claude` 호출 없음).
- 지원 기록 연결: 지원 기록에 종류별 **파일 이름만** 저장한다(각각 선택). 지원일과 **같은 날이거나 앞선** 파일 중 가장 늦은 것이 기본값이다. 그 종류의 가장 이른 파일보다 앞선 지원은 종류에 따라 다르다(2026-11-20 사용자 확인: 경력기술서·포트폴리오는 가장 이른 파일 전에는 없었고, 그때까지는 이력서만 냈다).
  - 이력서: **"모름"**(냈지만 어느 파일인지 모름).
  - 경력기술서·포트폴리오: **"없음"**(내지 않음).
  - 그 종류 파일이 폴더에 하나도 없으면 셋 다 "모름"이다(앱이 알 수 없음).
  - 예: 2026-08-01 지원 → 이력서 모름, 경력기술서 없음, 포트폴리오 `포트폴리오_20260722.pdf`. 2026-07-01 지원 → 이력서 모름, 경력기술서 없음, 포트폴리오 없음.
  - 직접 고를 때도 경력기술서·포트폴리오에는 "없음"이 있다. 이력서에는 "없음"이 없다(이력서는 늘 낸다).
  - 저장: 제출 서류 칸의 종류 값이 파일 이름 / "없음" 표식 / 빈 값(모름) 셋 중 하나다. 칸은 늘지 않는다.
- 보기: 지원 기록(대시보드의 기록만 행 펼침, 공고 상세 지원 기록 탭)에 종류별 [보기]를 두고, 누르면 앱이 그 폴더의 파일을 브라우저 새 탭에 PDF로 보여 준다. 이름 규칙과 종류 폴더 밖은 열지 않는다. 파일이 없어졌으면 "파일 없음".
- 이관: 메모에 "제출 서류: …" 줄이 있는 기록은 [메모의 제출 서류 옮기기]로 날짜를 파일 이름으로 바꿔 제출 서류 칸에 넣고 그 줄을 지운다(메모 첫 줄은 남김). 폴더에 없는 파일이 있으면 그 기록은 건드리지 않는다. 메모의 "모름"은 위 규칙대로 옮긴다(경력기술서·포트폴리오가 가장 이른 파일보다 앞선 지원이면 "없음").
- 대시보드 "이력서별" 보기: 앱 기본 이력서 버전이 없는 기록은 이력서 파일("이력서 2026-09-05")로 묶고, 둘 다 없으면 "모름". 3단계부터 맨 앞에 "맞춤 이력서", 그다음 "기본 서류 {직무}" 묶음.
- 앞으로의 [지원 완료]: 3단계부터 제출 서류 칸을 채운다(7.4, D-23). 이력서는 주로 맞춤본·기본 서류(키트, 7.11)로 기록된다. 그 전 [지원 완료] 기록은 제출 서류 칸이 비어 있다.

### 7.10 통계 [결정 D-18·D-19·D-20·D-21]

- 목적: 취업 전략을 세우는 데 쓴다. 언제, 어느 사이트에, 어떤 서류 버전으로 지원했을 때 서류가 잘 통과했는지 숫자와 그래프로 본다.
- 입력이 늘지 않는다. 지원 기록과 상태 이력만 읽는다. `claude` 호출과 스키마 변경은 없다.
- 위치: 새 화면 `/stats`. 상단 메뉴 "통계"와 대시보드 요약 줄 "통계 보기 →"로 들어간다(D-19).
- **결과 분류**: 지원 기록마다 아래 중 처음 맞는 것 하나로 센다(D-18).

  | 결과 | 조건 |
  |---|---|
  | 서류 통과 | 서류합격을 거침. 지금 상태 또는 상태 이력에 서류합격, 과제·코딩테스트, 면접, 최종합격 중 하나가 있다. 그 뒤 불합격·지원취소가 되어도 통과다. 지금 상태가 지원이면 통과가 아니다(7.2와 같은 규칙) |
  | 지원취소 | 지금 상태 지원취소 |
  | 불합격 | 지금 상태 불합격 |
  | 대기 | 지금 상태 지원이고, 지원일부터 30일이 안 됨 |
  | 무응답 | 지금 상태 지원이고, 30일 이상 지남 |

- **서류 통과율** = 통과 ÷ (통과 + 불합격 + 무응답). 대기와 지원취소는 분모에서 뺀다. 참고용으로 판정 기준 통과율(통과 ÷ (통과 + 불합격))도 보여 준다.
- 표본 표시: 분모가 0이면 "–", 1~4면 "표본 부족", 5~19면 "표본 적음" 배지를 단다. 비율 옆에는 항상 분자/분모를 쓴다.
- 기간 기준은 지원일이다. 필터는 기간(전체 / 최근 3개월 / 최근 1년 / 직접 지정)과 사이트다.
- 보여 주는 것(D-21)

  | 통계 | 내용 |
  |---|---|
  | 요약 카드 | 지원, 서류 통과(과제·코딩테스트, 면접, 최종합격을 거친 수), 서류 통과율, 무응답 비율, 대기, 지원취소 |
  | 기간별 | 월별·연별 지원 수와 결과(누적 막대), 서류 통과율 |
  | 서류 버전별 | 이력서·경력기술서·포트폴리오 중 하나를 골라, 버전(기본 이력서 버전 또는 파일 날짜, 7.9)마다 지원 수와 서류 통과율, 그 버전을 쓴 기간. 이력서는 3단계부터 맨 앞에 "맞춤 이력서" 묶음 |
  | 맞춤 이력서 효과 (3단계, D-24 결정) | 맞춤본을 처음 낸 날부터의 지원만 "맞춤 이력서 / 맞춤 안 함" 두 줄로 지원 수와 서류 통과율 비교. 맞춤형 지원 방향이 효과가 있는지 판단하는 데 쓴다 |
  | 프로필별 (3단계, D-29 추천안·결정 대기) | 프로필(맞춤본·기본 서류)마다 지원 수, 서류 통과율, 그중 맞춤 수. 기본 프로필을 바꿀지 판단하는 데 쓴다 |
  | 사이트별 | 사이트마다 지원 수, 서류 통과율, 무응답 비율 |
  | 단계별 흐름 | 지원 → 서류 통과 → (과제·코딩테스트) → 면접 → 최종합격을 거친 수와 앞 단계 대비 비율. 과제·코딩테스트는 거치지 않을 수 있어 곁가지로 보이고, 과제와 면접의 비율은 둘 다 서류 통과 대비다 |
  | 요일별 | 지원 요일별 지원 수와 서류 통과율 |

- 그래프는 외부 라이브러리 없이 직접 그린다(D-20). 모든 그래프 아래에 같은 숫자의 표를 둔다.
- 만들지 않는 것
  - 서류 통과까지 걸린 일수(D-21)
  - 시간대별 통계. 정렬용 일시가 실제 시각이 아닐 수 있다(D-17).
  - 같은 회사 재지원, 적합도별, 포지션 키워드별 통계
  - 상태 일괄 변경
  - 통계 내보내기
- 화면 상세: 화면 문서 10장. 계획: `docs/plans/phase-2-stats.md`

### 7.11 서류 키트 (3단계, D-27 추천안·결정 대기)

- 맞춤 이력서(7.5)의 재료. 사용자가 앱 밖에서 직접 관리하는 문서들의 **사본**이다.
  - 공고 맞춤 가이드: 직무별 기본 서류 목록, 부품 번호표, 프로필별 레시피(공고 단어·자기소개 후보·순서·개인 프로젝트), 추가 조정, 자기소개 후보, 표현 허용 범위, 제출 전 체크리스트
  - 작성 규칙, 마스터스토리(사실 원본)
  - 직무별 기본 이력서·경력기술서 md
  - (선택) PDF 스타일(CSS)
- 넣는 방법: 기본 이력서 화면의 "서류 키트"에서 파일들을 골라 올린다. 앱은 원본 폴더(`D:\` 등)를 읽지 않는다. 원본을 고치면 다시 올린다. 올릴 때마다 새 키트 버전이 생기고, 옛 버전은 남는다(옛 맞춤본이 그 버전을 쓴다).
- 앱은 가이드를 **코드로 읽어** 구조(직무·프로필·레시피 등)를 저장한다. 프로필 추천과 자동 검사, 통계의 프로필 이름이 이것을 쓴다. 형식이 맞지 않으면 어디가 틀렸는지 보여 주고, 그 키트로는 맞춤본을 만들지 않는다. 앱이 읽는 형식은 3단계 계획 "서류 키트 형식"에 있다.
- 키트 파일은 데이터 폴더(`data/kit/`) 안에만 있다. 저장소·문서·테스트로 옮기지 않는다(공개 저장소).
- 앱 안 기본 이력서(7.1)와의 관계: 기본 이력서는 **공고 분석의 기준**으로만 남는다. 맞춤본과 PDF는 키트로 만든다. 분석도 키트 기준으로 바꾸는 것은 다음 작업 후보다.
- 지난 서류 파일(7.9, `이력서_YYYYMMDD.pdf`)은 지난 기록용으로 그대로 둔다. "직무별 변형은 무시" 규칙은 그 파일들에만 해당한다. 앞으로의 지원은 키트의 직무·프로필로 기록한다.

## 8. 공고 본문 추출 [제안]

- 앱이 Playwright(Chromium)로 URL을 열고 렌더링이 끝난 뒤 본문 텍스트를 추출한다.
- **브라우저 프로필을 앱 데이터 폴더에 영구 저장**한다. 로그인이 필요한 사이트(예: 리멤버)는 사용자가 앱의 [사이트 로그인] 버튼으로 뜬 브라우저 창에서 **직접 한 번 로그인**해 두면, 이후 추출 시 그 로그인 상태를 쓴다. 앱은 비밀번호를 입력하거나 저장하지 않는다.
- 사이트별 본문 영역 선택 규칙을 두되, 실패하면 페이지 전체 텍스트를 쓰고 Claude가 분석 단계에서 공고 부분만 골라낸다.
- 추출 실패(로그인 벽, 차단, 빈 본문) → 화면에 "본문을 붙여넣어 주세요" 입력창을 띄운다.
- 사이트 상대로 반복 요청하지 않는다: 공고 1건당 사용자 요청 시 1회만 연다.

## 9. AI 실행 계층 (Claude Code CLI)

### 9.1 호출 방식

- 앱 서버가 자식 프로세스로 `claude -p`(비대화형 출력 모드)를 실행한다.
- 입력은 **표준입력 또는 임시 파일**로 전달한다(Windows 명령줄 길이 제한).
- 결과는 JSON 출력 형식으로 받아 응답 본문을 파싱한다(세션 ID는 형식 오류 재요청에만 쓴다).
- 작업별로 모델을 설정할 수 있게 한다. 기본값: 판단이 필요한 작업(공고 분석, 맞춤 이력서·다듬기, 면접 준비·추가 요청)은 Opus, 옮겨 적는 작업(이력서 가져오기, 지원 내역 가져오기, 사이트 반영)은 Sonnet. [결정 D-05]
- 정확한 CLI 옵션 이름(출력 형식, 모델 지정, 허용 도구, 세션 이어가기, 최대 턴 수, 권한 모드)은 **설치된 Claude Code 버전의 `claude --help`로 확인**해 쓴다. 문서와 버전 간 차이가 있을 수 있다.

### 9.2 안전장치

- **작업 디렉터리**: 앱 프로젝트 폴더가 아닌 전용 작업 폴더(`data/ai-work/<job-id>/`)에서 실행한다. 입력 파일을 거기에 두고 Claude Code가 읽게 한다.
- **허용 도구 제한**: 작업별 최소 권한.
  - 공고 분석·맞춤 이력서: 작업 폴더 파일 읽기만.
  - 면접 준비: 파일 읽기 + 웹 검색 + 웹 페이지 읽기.
  - 기존 내역 가져오기: 작업 폴더 파일 읽기(이미지 포함).
  - 셸 실행, 파일 쓰기/수정은 모든 작업에서 금지. 결과는 응답(JSON)으로만 받고 저장은 앱이 한다.
- **결과 검증**: 작업별 JSON 스키마(zod)로 검증. 형식 오류 시 같은 세션에 "형식에 맞춰 다시"를 1회 요청, 그래도 실패하면 오류 표시 + 원문 보관.
- **로그인 정보 비접근**: 앱은 Claude Code의 인증 파일·토큰을 읽지 않는다. 로그인 안 된 상태면 "터미널에서 `claude`로 로그인하세요" 안내만 한다.

### 9.3 작업 큐

- AI 작업은 DB의 작업 테이블에 쌓고 **한 번에 하나씩** 실행한다(사용 한도·PC 부하 고려). [제안]
- 상태: 대기 → 실행 중 → 완료 | 실패 | 취소. 화면은 주기적으로 상태를 조회해 진행 표시를 한다.
- 시간 제한: 분석·맞춤 이력서 5분, 면접 준비 10분 (설정 가능). [제안]
- 사용 한도 도달 등 Claude Code 오류는 메시지를 사용자에게 그대로 보여주고 [다시 시도]를 제공한다.
- 작업마다 실행 시간, 세션 ID, CLI가 보고하는 사용량 정보(있으면)를 기록한다.
- 앱 재시작 시 "실행 중"으로 남은 작업은 실패 처리 후 재시도 가능하게 한다.

### 9.4 대화로 다듬기 (D-11)

- 다듬기 요청마다 **새 실행**으로 처리한다. 프롬프트에 기준 이력서, 공고, 현재 리비전(JSON), 요청을 모두 넣는다.
- 이전 대화(세션)를 이어 붙이지 않는다. 작업 폴더를 작업마다 새로 쓰고 끝나면 지우기 때문이다(D-09).
- 요청 내용은 리비전마다 기록해, 무엇을 왜 바꿨는지 따라갈 수 있게 한다.
- 면접 준비의 추가 요청도 같은 방식이다.

### 9.5 프롬프트 관리

- 작업별 프롬프트는 코드와 분리된 파일(`prompts/*.md`)로 둔다. 출력 JSON 스키마도 프롬프트에 포함한다.
- 맞춤 이력서 프롬프트에는 "기본 이력서에 없는 사실 추가 금지" 규칙을 최상단에 둔다.

- 공고 상태(`postings.status`)는 지원 전 단계(분석함 등), 지원 이후는 `applications.status`로 관리. 세부 분리 방식은 구현자 재량.
- 회사 매칭: 분석 결과의 회사명으로 기존 `companies`를 정규화 키로 찾아 연결, 없으면 생성. 사용자가 공고 화면에서 회사 연결을 바꾸거나 별칭을 추가할 수 있다. [제안]
- 중복 경고: 공고 등록·분석 후 연결된 회사에 `applications`가 있으면 경고 배너 표시.

## 11. PDF 출력 [제안]

- 맞춤본(또는 기본 이력서) JSON → HTML 이력서 템플릿 → Playwright로 A4 PDF 출력.
- 한글 웹폰트(예: Pretendard)를 앱에 포함해 PC 글꼴과 무관하게 동일하게 출력.
- 1차 범위는 깔끔한 템플릿 1종. 템플릿 추가는 나중에.
- 파일명 규칙: `이름_회사_포지션_YYYYMMDD.pdf`.
- 이력서와 경력기술서를 한 PDF로 묶을지, 따로 받을지 선택. [제안]
- 받은 PDF는 앱에 파일로 보관하지 않는다(D-25 결정). 한글 낱말이 줄 끝에서 끊기지 않게 한다.
- 재설계 1(프로필 방식): 입력은 JSON이 아니라 키트의 md다. md → HTML(제목·프로필 상자, 큰 제목마다 섹션) → 키트 스타일 CSS(없으면 앱 기본) → A4 PDF. 이력서와 경력기술서는 따로 받는다. 파일명은 키트 가이드 규칙 `이름_이력서|경력기술서_직무.pdf`. 앱 기본 이력서(JSON)의 PDF는 만들지 않는다.

## 12. 화면 구성 [제안]

1. **대시보드**: 보기 전환(전체 / 사이트별 / 상태별 보드 / 이력서별), 검색창, 필터, 지원 목록 표, 요약 지표, "분석한 공고" 바로가기, 상단에 [공고 등록] 버튼.
2. **공고 등록**: URL 입력(+ 본문 붙여넣기 대안) → 등록 즉시 분석 진행 표시 → 완료 시 공고 상세로 이동.
3. **공고 상세**: 탭 구성 — 공고 원문 / 분석 / 맞춤 이력서(리비전, 변경 내역, 사이트 수정 안내, PDF, 수정 요청 입력창) / 면접 준비 / 지원 기록·타임라인. 상단에 중복 경고 배너, [지원 완료] 버튼, 상태 변경.
4. **기본 이력서**: 구조화된 편집 화면, 버전 목록·비교, 희망 조건.
5. **가져오기**: 기존 지원 내역 붙여넣기/이미지 → 검토 표 → 일괄 등록. 또는 직접 입력(빈 검토 표).
6. **사이트 반영 체크리스트**: 버전 변경별·사이트별 반영 항목.
7. **설정**: 작업별 모델, 시간 제한, 사이트 로그인(브라우저 프로필), 데이터 폴더 위치, 백업.
8. **통계**(`/stats`): 요약 카드, 기간별·서류 버전별·사이트별·단계별·요일별 서류 통과율과 그래프(7.10).

화면별 상세 구성(보여주는 데이터, 버튼과 동작, 상황별 표시): `docs/spec/screens.md`

## 13. 기술 구성

| 영역 | 선택 | 근거 |
|---|---|---|
| 언어 | **TypeScript** [사용자 결정] | |
| 앱 | **Next.js** (App Router, 서버 액션/라우트 핸들러) [사용자 결정] | 화면·서버 한 프로젝트 |
| DB | **SQLite** (+ 타입 안전한 ORM/쿼리 빌더, 예: Drizzle) [제안] | 설치 불필요, 파일 하나로 백업 |

| 공고 추출·PDF | **Playwright (Chromium)** [제안] | JS 렌더링 사이트 대응, HTML→PDF |
| AI | **Claude Code CLI (`claude -p`)**, 사용자 구독 로그인 [사용자 결정] | 추가 비용 없음 |
| UI | 구현자 재량 (예: Tailwind + 기본 컴포넌트 라이브러리) | |
| 실행 | `npm run start` 로 로컬 실행, 바탕화면 바로가기 스크립트 [제안] | |

- 데이터 폴더(`data/`): SQLite 파일, 업로드 원본, AI 작업 폴더, 생성된 PDF, 브라우저 프로필. 소스 코드와 분리하고 git에서 제외.
- 백업: 앱 시작 시 하루 1회 SQLite 파일을 `data/backups/`에 날짜별 복사(최근 30개 보관). [제안]

## 14. 구현 단계 [제안]

1. **기반**: 프로젝트 생성, DB 스키마, 데이터 폴더, AI 실행기(큐·CLI 호출·검증), 기본 이력서 등록/편집/버전.
2. **핵심 문제 해결 (MVP)**: 공고 등록 → 본문 추출 → 자동 분석, 회사 매칭·중복 경고, 지원 완료·상태 관리, 대시보드·검색, 기존 지원 내역 가져오기.
3. **맞춤 이력서**: 생성, 변경 내역, 사이트 수정 안내, 대화로 다듬기, PDF 출력.
4. **면접 준비**: 웹 조사 포함 생성, 차수별 관리, 대화로 추가 요청.
5. **사이트 반영 체크리스트**, 설정·백업 마무리.

2단계까지 끝나면 "어디에 언제 지원했는지 모름 / 중복 지원" 문제는 해결된다.
